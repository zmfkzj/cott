# trait-protocol

## Purpose
This Cott v0.7 lesson puts trait inheritance, selection, exact runtime views, and async state ownership in one `SimpleTask` implementation.

## Trait selection and exact types
- `Summarizable` preserves the associated `Summary` type through `summary() -> Summarizable.Summary`; covariant `TaskView[+T]` inherits it together with `Prioritizable` and uses `T` for `display`. `SimpleTask` selects `TaskView[Str]`, assigns `Summary = Str`, and therefore gives `Dyn[TaskView[Str]]` an exact generic trait identity rather than a structural substitute.
- Every effective slot is async because a single impl cannot mix sync and async trait slots. `summary` and `priority_level` are explicit methods whose clauses fix their results: `result == self.title` and `result == self.urgency`. `display` is selected by `specialize SimpleTask for TaskView[Str]` and dispatches through `specialized_display`, whose three clauses (`starts_with(result, "specialized: ")`, `ends_with(result, receiver.title)`, and `result.len == receiver.title.len + 13`) determine the text exactly. `category` has no method of its own and dispatches through `default_category`, which ensures `result == "default"`. Trait methods carry no clauses; the selected free function's contract is the dispatched slot's contract.
- `task_factory() -> Factory[SimpleTask]` returns the generated `SimpleTask` class itself without constructing it. The Python `Factory` boundary accepts only that exact class. The app prints the identity check before calling the factory.
- `inspect_dyn` awaits a method through the `Dyn[TaskView[Str]]` view. Clauses cannot call trait methods, so requirement `DYN_VIEW_RETURNS_SUMMARY` states that the result is the view's `summary()`, not its `display()` or `category()`. The authored scenario links this requirement to its exact dynamic-summary assertion.

## State and observable behavior
- The compiler owns `title`, `urgency`, `lifecycle`, `completion_count`, initialization, locks, and wrappers. Its invariants require a nonempty title, nonnegative urgency, and nonnegative completion count; `init(title, urgency)` preserves the two caller-supplied fields.
- `await task.complete()` is the one explicit async state transition. It changes `lifecycle` only through `Pending -> Completed`, increments the non-resource `completion_count` under `modifies`, and states that increment with `old(self.completion_count)`. `modifies` deliberately does not name the resource field because its transition owns that update.
- The app awaits the explicit, specialized, default, Dyn, priority, and completion calls. A second `await task.complete()` has no declared `Completed -> Completed` edge and the generated boundary raises its transition violation; the example does not catch or hide that error.

## Evidence
- Bounded runner cases build `SimpleTask` from its `init` and observe the `init`, `summary`, `priority_level` and `complete` clauses and the invariants on every slot, including `display` and `category`. The Python candidate generator cannot construct the trait-typed `receiver` input of `default_category` or `specialized_display`, so their `ensures` clauses remain `unknown` (unobserved) here.
- The mirrored `dyn_view_dispatches_summary` scenario constructs `SimpleTask(title: "Launch", urgency: 1)` through the public facade, calls `task.summary()`, wraps the task in `Dyn[TaskView[Str]]`, and asserts that `inspect_dyn(view)` returns exactly `"Launch"`. The requirement links to that final assertion (assertion 2). The app separately demonstrates the different specialized `display()` and default `category()` outputs.
- `cott verify` executed this scenario and certified the snapshot in this project and in the Kotlin mirror (`examples/kotlin/features/trait-protocol`): Python graded both assertions `test observation`, and the Kotlin runner reported the scenario `passed` with both assertions. `cott requirements` reports `DYN_VIEW_RETURNS_SUMMARY` as `observed` against the `current` snapshot in both projects. This is bounded evidence for one task value, not a proof of the requirement. The app's `Dyn:` line remains a separate external regression, not Cott scenario evidence.
